# Trading-Analysis

Учебный проект для сбора и анализа дневных свечей MOEX. Совмещает Java-бэкенд (надёжный сбор данных) и Python-аналитику (статистика, индикаторы, модель), с целью прокачать инженерные навыки и позже вывести систему в облако.

> Статус: в разработке. Аналитика — исследовательская, **не торговая рекомендация**.

## Архитектура

```
MOEX API → Java collector → PostgreSQL → Python analysis → Desktop UI (PyQt)
```

| Компонент | Технологии | Задача |
|---|---|---|
| **Java collector** | Spring Boot, `MoexDataService`, `DataCollectionScheduler` | Забирает дневные свечи с MOEX, проверяет их и пишет в БД |
| **PostgreSQL** | Flyway (миграции) | Хранит свечи и справочник инструментов |
| **Python analysis** | pandas, statsmodels, scikit-learn/XGBoost | Считает индикаторы, статистику, обучает и оценивает модель |
| **Desktop UI** | PyQt | Локальный просмотр графиков, индикаторов и результатов модели |

Каждый компонент решает одну задачу и не дублирует логику других: индикаторы считаются в одном месте и используются и в UI, и при обучении модели.

## Как запустить локально

> ⚠️ Раздел временный — уточнить и проверить перед коммитом. Ниже — предполагаемый минимум.

**Требования:** Java 17+, PostgreSQL 14+, Python 3.10+, Maven.

```bash
# 1. Поднять БД
docker-compose up -d postgres

# 2. Собрать и запустить Java-сборщик
cd java-collector
./mvnw spring-boot:run

# 3. Установить зависимости Python-модуля
cd ../python-analytics
pip install -r requirements.txt   # уточнить: включает ли xgboost, scikit-learn

# 4. Запустить desktop-приложение
python main.py
```

Секреты (пароль БД, при необходимости — токен MOEX) передаются через переменные окружения, не хранятся в репозитории.

## Данные и целевая переменная модели

- Таргет модели — доходность за горизонт `h` торговых сессий (или факт превышения порога).
- Обучающая выборка **не должна** включать последние `h` строк, для которых ещё неизвестен результат в будущем — иначе таргет ошибочно помечается как отрицательный.
- Валидация — последовательное разбиение по времени, с защитным промежутком (embargo) перед тестовым периодом, чтобы исключить утечку через пересекающиеся горизонты.
- Модель всегда сравнивается с базовыми подходами (константный класс, историческая частота), не только по accuracy — также precision/recall, матрица ошибок.

## Дорожная карта

1. **Стабилизация локально** — починить баг с таргетом, единый модуль индикаторов, надёжный Java-сборщик, статистический профиль данных.
2. **Docker для разработки** — PostgreSQL + Java-сборщик в Compose; Python-анализ в headless-режиме (без PyQt) для последующей контейнеризации.
3. **CI/CD** — отдельные workflow для Java (сборка + тесты), Python (зависимости + pytest), Docker (build на PR, publish после мержа).
4. **Перенос вычислений на удалённый сервер** — сборщик, БД и headless-анализ переезжают на VPS; desktop-приложение остаётся локальным клиентом.
5. **Telegram-бот** — подписки на тикеры, утренняя сводка + внутридневные алерты поверх уже работающего облачного пайплайна.
